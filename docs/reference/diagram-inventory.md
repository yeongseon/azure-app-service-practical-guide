# Diagram Inventory and Migration Manifest

This reference inventories App Service diagram sources for #282 under parent #281. It records source facts and proposed work ownership, not completed migration, reviewed genres, source verification, or rendered visual correctness.

## Purpose and Scope

The [machine-readable manifest](diagram-manifest.json), governed by the [shared inventory schema](diagram-manifest.schema.json), records each Mermaid occurrence with its page-qualified key, source location, heading context, syntax, candidate genre, declared provenance, structural baseline, owner and migration state. The [ADR](adr-diagram-composition.md) explains alternatives and the dependency on #283.

`context.reader_intent` deliberately remains null until reviewed. Target base, extensions and overlays are provisional, not approved composition destinations. `migration.state` remains `not-started`. Evidence-oriented intent is not inferred as a separate syntax type: a lab evidence timeline can be a flowchart or timeline, and must retain its evidence meaning during later review.

## Counting Policy

Every Mermaid fence in tracked Markdown is one occurrence; equal source bodies remain separate occurrences. An asset referenced repeatedly is one asset with multiple usages. The manifest records baseline commit `036376dff4e4c2e919470b51a1cb89ef708d88ea`; counts describe the working tree inventoried for that baseline:

- 405 occurrences appear in 246 diagram-bearing Markdown files. The committed tree has 286 tracked Markdown files, including these inventory, ADR and topology grammar pages (`git ls-files '*.md'`).
- 404 are published under `docs/`; one is a repository-only authoring example in `DOCUMENTATION_CONTRACT.md`.
- Ten occurrences are excluded: the authoring example, three generated dashboards (content validation, tutorial validation, Golden status) and, since [#296](https://github.com/yeongseon/azure-app-service-practical-guide/issues/296), the six illustrative fixtures of the topology visual grammar.
- 395 Mermaid occurrences require migration; their batch counts sum to 395.
- `visuals[]` separately records two interactive Cytoscape navigation graphs and one removed learning-path placeholder group, all explicitly excluded from the Mermaid migration (see Non-Mermaid Visuals). The removal record preserves inventory history; these records are not added to Mermaid batch totals.
- Asset exclusions cover 106 WebPs, six legacy PNGs and two branding SVGs, each in exactly one group. There are no tracked standalone Mermaid, draw.io, PlantUML, or Excalidraw sources.

## Command Reference

Use Python 3.11 with PyYAML; `jsonschema` is optional locally and installed in CI. Commands run from the repository root; the scanner also resolves its root independently of the caller's working directory. It never renders, converts, or verifies source provenance. `--write` writes the manifest and this page's generated blocks; `--check` performs consistency validation, not provenance verification.

Files are decoded as UTF-8 with optional BOM. An undecodable file is skipped and recorded in `frontmatter_unparseable` with its path and decoding error, like unparseable frontmatter; this exception means extraction is incomplete, not that no diagram exists. Duplicate usable frontmatter IDs appear in `frontmatter_duplicate_ids`; only the first entry supplies declared provenance. Missing, null, empty, or non-string frontmatter IDs never attach to a fence.

The scanner is a line-based approximation of how the site renders indentation, not a full Markdown container parser. It errs toward reporting Mermaid-opener-like lines in `unrecognized_mermaid_fences` rather than silently dropping them:

- `html-comment` and `indented-code` are informational: the fence is hidden by a multiline HTML comment or shown as plain indented code. Plain-code state starts at an indented line (at least four columns, with tabs expanded) after a blank line or at the start of the page, while no HTML element is open and no list or container ancestor applies. It continues across blank or indented lines and ends at the first nonblank line with fewer than four columns. A heading or thematic break ends a list, and a line indented four columns or more is code, not a list item. `--check` prints each finding without failing.
- `blockquote`, `list-marker`, and `indented` are blocking findings. The last reason covers container indentation, an indented fence while an HTML element is open, and a lazy continuation directly after prose without a blank line. HTML context starts from a tag at the beginning of a line (up to three spaces of indentation), including a visible tag next to a comment. Tags on that line are processed in order with case-insensitive names: an opener pushes its name; a closing tag removes the nearest matching element and its descendants, or is ignored if none is open. Single- and double-quoted attributes protect embedded `<`, `>` and closing-tag text; only `/>` outside quotes ends a self-closing tag. Void elements, comments, declarations, processing instructions, inline-code spans and fenced-code contents open nothing. An unfinished start tag opens provisionally and retains its quoted state across lines; completion applies its actual closing syntax, while an unterminated tag remains conservatively open. Intervening paragraphs, headings, lists and code blocks do not close an element. Inside `pre`, `script`, `style` and `textarea`, tag-looking text other than that element's closer does not change the stack. This is still a heuristic, not a rendering guarantee: indented fences inside open elements are blocking even where the site shows plain code. `--write` succeeds and warns once per page, listing only blocking findings; `--check` fails. Move the fence to the top level with at most three spaces of indentation, or show it inside a longer outer fence, then regenerate.
- Fence recognition precedes comment detection. Inline code spans containing comment tokens do not open comments. A multiline comment needs a closing `-->`: an unclosed one is shown as literal text by the site, so it hides nothing, and text inside any fence never closes a comment because the site extracts fences first. Unsupported blocks, including indented generic fences of any language or no language, are consumed through their matching closing fence (even a dedented closer) so later canonical fences remain in sync; shorter fences of the same kind and fences of another kind inside the block are content, and only Mermaid openers produce findings. Another opener of the same kind and at least the same length before a closing fence, or no closing fence, means the block is unclosed and the scan resumes on the next line instead of swallowing the page.
- Recognized outer non-Mermaid fences contain examples, not rendered diagrams, and do not produce unsupported-fence findings. The separate `scripts/validate_mermaid_format.py` policy already rejects indented Mermaid fences, including plain indented code examples; use a longer outer fence for examples.

The shared scanner's classification was checked against Python-Markdown 3.10.2 and pymdownx 10.21.3 on 2026-10-30 in local experiments with synthetic corpora, run for the Container Apps pull request #415 and described on that guide's inventory page; their harnesses and evidence are not committed here, and the experiments were not rerun for App Service. The scan result of every Markdown file of this repository is identical between the previous and the current scanner version. The measurements do not estimate how often such patterns occur in real documentation and are not a rendering guarantee: corrupted or unbalanced fence syntax and heuristic HTML context remain disclosed limitations.

Known limitations:

- Info strings with extra words are counted by the first-word `mermaid` rule, but the site shows them as code rather than diagrams.
- A comment that starts after a list marker or blockquote prefix is not tracked.
- Nested list/container structure beyond the less-indented ancestor heuristic may be reported as `indented` when the site shows code. Space-separated thematic breaks are checked before list markers; tabs can change the site's interpretation and are not interchangeable with spaces. Setext headings and deeply nested list boundaries remain heuristic. Plain-code continuation is tracked explicitly, but this is not a full container parser.
- HTML context remains a line-start heuristic. A closer in ordinary prose rather than on a tag-starting line can leave stale context. Never-closed elements include plausible inline anchors such as `<a name="x">` and `<span>`, as well as `<p>`, `<li>` and table cells whose end tags HTML permits omitting; implicit closure is not modeled. Incomplete tags, omitted end tags, overlapping elements and raw-text contents are not a full HTML parse. Raw-text tracking protects the element stack, but does not reproduce every interaction between HTML, Markdown and fence extraction. The false-block direction is deliberately conservative: dedented bodies under a simple wrapper, raw-text examples and unfinished elements can show no diagram while still blocking. The tokenizer/list experiments above exercise these limits without establishing exhaustive equivalence.
- Corrupted or unbalanced fence syntax, for example an opener that is never closed, bare marker lines of a different kind, tilde/backtick mixes, or fence markers and comment tokens inside an info string, is parsed differently by CommonMark and by the site's renderer. The scanner uses CommonMark-style boundaries for recognized top-level fences and records their unclosed fences in `unclosed_fences`, but the site can show more diagrams than the scanner accounts for on such a page.

```bash
python scripts/test_diagram_inventory.py
python scripts/diagram_inventory.py --check
```

`--check` validates schema, keys, owning batches, reconciliation, pinned hashes and generated blocks. It does not compare current source to the committed snapshot, render diagrams, or verify provenance. Deterministic fixture reproduction remains blocking; current-tree baseline reproduction is opt-in with `DIAGRAM_INVENTORY_REPRODUCE=1` when the tree is unchanged. The comparison of the tree with the snapshot that `--check` does not make is made by the guard in the next section.

### Guarding Manifest Coverage (Blocking CI)

```bash
python scripts/test_check_diagram_manifest_coverage.py
python scripts/check_diagram_manifest_coverage.py
```

`scripts/check_diagram_manifest_coverage.py` is the repository-local guard for [#394](https://github.com/yeongseon/azure-app-service-practical-guide/issues/394). It imports `scripts/diagram_inventory.py` without changing it, so no repository-specific logic enters the shared scanner and schema, whose updates the [ADR](adr-diagram-composition.md) requires to be coordinated byte-identically with the sibling guides; it renders nothing. It needs the same Python 3.11 and PyYAML as the scanner. It first runs the scanner's consistency checks and stops with their errors if the manifest is inconsistent. It then scans the Markdown files that Git tracks, as they are in the working tree (stage a new page before running the guard), and compares the result with the committed manifest:

| Finding | Reported when | Applies to |
|---|---|---|
| `Mermaid occurrence is not in the manifest` | A fence exists in the tree and has no manifest record (uncovered). | Every entry |
| `Mermaid fence cannot be recognized, so the manifest cannot cover it` | The scan of the tree reports a fence in `unrecognized_mermaid_fences` with a blocking reason (`blockquote`, `list-marker` or `indented`). Fix the page: regenerating the manifest would only make the scanner's `--check` fail on the same fence. | The fence |
| `manifest record has no Mermaid occurrence in the tree` | A record has no fence in the tree (stale), for example after its page was deleted. | Every entry |
| `now <key> in the tree` | A record's body appears under another key, after a page or `diagram-id` rename. | Every entry |
| `source differs from the manifest`, `provenance differs from the manifest` | The body hash or the declared provenance of the entry no longer matches the manifest. | `in-progress` and `completed` entries |
| `requires a stable diagram-id comment`, `requires declared source provenance` | The entry has no stable `diagram-id` comment, or its page declares no source for that ID. | `in-progress` and `completed` entries |
| `is not the composition base`, `unknown extension`, `unknown overlay` | The `target` of the entry names a base, extension or overlay that `scripts/diagram_composition.json` does not define. | `in-progress` and `completed` entries with a `target` |
| `is not enrolled in`, `composition target requires scripts/diagram_composition.json` | The `target` of the entry names a composition, but the spec does not enroll that diagram or the spec file does not exist. | `in-progress` and `completed` entries with a `target` |
| `differs from the enrolled composition` | The `target` of the entry is not the selection (base, extensions in the same order, and overlay) that the spec enrolls for that diagram. An empty `target` differs from the selection of an enrolled diagram. | `in-progress` and `completed` entries with a `target`, and those whose diagram the spec enrolls |
| `composition output is not in the manifest` | A diagram enrolled in `scripts/diagram_composition.json` has no manifest record. The `page` of the diagram is compared after pathlib-style normalization, so `docs/./x.md` is `docs/x.md`. | Every enrolled diagram |
| `unreadable composition spec` | The spec path exists (a dangling symlink counts as existing) but cannot be read as JSON of the shape that the guard reads: the file cannot be opened or decoded, an object of the file repeats a key, or it is not an object whose `base.id` is text, whose `extensions` and `overlays` are objects and whose `diagrams` is a list of objects with text `page`, `id` and `base`, a list of text `extensions` and a text or null `overlay`; or the `page` of a diagram leaves the repository. The guard checks no other part of the spec: the composer and its tests validate the rest. When Git lists the spec as a symlink that leaves the repository, or, before Python 3.13, as a symlink that loops, the scanner's file walk fails first and the guard prints that one-line error instead of this finding. | The spec file |

Edits to the body or provenance of a `not-started` or `exception` entry, line moves and changed classifications are not reported; `--verify-tree` still lists them as advisory drift. The guard therefore requires no diagram to be migrated. At the baseline every entry is `not-started`, so only the tree-coverage findings (including the unrecognized-fence finding), the enrolled-diagram finding and the unreadable-spec finding can occur until an owner starts a migration.

After a pull request adds or removes a Mermaid fence, moves one to another page, or renames its page or its `diagram-id`, regenerate and commit the manifest with `python scripts/diagram_inventory.py --write` (see Regenerating the Manifest). The manifest is the authority for which occurrences are in scope. Two pull requests that each change fences can therefore conflict in it, or merge without a conflict into a manifest that matches neither tree (for example when both raise a total to the same value); the checks can then fail on `main` after the second merge until the manifest is regenerated and committed. Resolve it by regenerating the manifest, not by merging it by hand.

Coverage means what the scanner extracts, so the scanner's [known limitations](#command-reference) apply to it: a fence that the scanner reports only informationally (hidden by an HTML comment, or shown as plain indented code) or that sits on a page with corrupted or unbalanced fence syntax may be absent from the manifest, and the guard does not report it. The guard is not an equivalence with what the site renders. It does not render a diagram, verify a declared source, or establish that a migrated diagram renders correctly. Render inspection and the target of zero unconverted in-scope diagrams stay with [#289](https://github.com/yeongseon/azure-app-service-practical-guide/issues/289). The composition checks read `scripts/diagram_composition.json` as plain JSON and never import the prototype, so removing the opt-in [composition prototype](diagram-composition-prototype.md) does not change the guard. A composed fence that has drifted from its spec is not checked here: `tests/ci/test_diagram_composition.py` compares every committed fence with the body its spec composes, and the Operating contract tests job runs it on every pull request.

### Regenerating the Manifest

`--write` reads the current working tree and regenerates the whole manifest, recording `baseline.base_commit` as metadata (pass `--base-commit` to pin it); it does not read the tree at that commit or retain separate baseline records and current-tree observations. Run `--verify-tree` before rewriting to see removed and changed records. Reviewed planning fields are preserved by key, while a reviewed classification is preserved only when the diagram body's `baseline.source_sha256` is unchanged; a changed body receives a fresh, unreviewed heuristic classification and must be reviewed again.

```bash
python scripts/diagram_inventory.py --write --base-commit "$(git rev-parse HEAD)"
```

Use an explicitly reviewed baseline commit when rebasing the inventory. Without an override, subsequent writes preserve the existing base commit. Do not edit the manifest or generated blocks by hand.

### Migration Progress States

Batch owners edit `target`, `context.reader_intent`, and `migration` by key; these planning fields survive body changes and regeneration.

| Migration state | Meaning | `exception` |
|---|---|---|
| `not-started` | Migration has not begun. | `null` |
| `in-progress` | The owning batch is migrating the diagram. | `null` |
| `completed` | The owning batch records migration as complete. | `null` |
| `exception` | Migration has an explicitly recorded exception. | Nonblank explanation string |

These are owner-maintained progress states, not proof of rendering, source verification, or review approval. The [coverage guard](#guarding-manifest-coverage-blocking-ci) checks an `in-progress` or `completed` entry against the tree and the composition spec; it checks a `not-started` or `exception` entry only for the coverage of its occurrence.

### Checking Tree Drift (Advisory)

```bash
python scripts/diagram_inventory.py --verify-tree
```

This compares extracted diagram records with the baseline; it does not report extraction completeness. Consult `unrecognized_mermaid_fences` through `--check` for blocking extraction findings. A drift-free result alone does not establish a complete inventory.

The JSON categories are `added` and `removed` keys; `moved` key changes with identical bodies; `changed` body hashes; `reclassified` genre, syntax type, or assignment changes; `provenance` changes to the complete provenance record; and `relocated` changes to the same key's line, end line, or heading path. `assets` lists changed exclusion-group path sets as `{group, added, removed}` records, with `group: null` for the unclassified-asset set; `visuals` lists keys added, removed, or changed in non-Mermaid visual records. Paths are compared as sets, not list order. Drift remains advisory (exit zero); adding `--strict` makes any non-empty category fail. The [coverage guard](#guarding-manifest-coverage-blocking-ci) makes `added`, `removed` and `moved` blocking, and `changed` and `provenance` blocking for started migrations only; `reclassified`, `relocated`, `assets` and `visuals` stay advisory. This does not refresh Azure capture or validation dates.
