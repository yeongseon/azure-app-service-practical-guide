# Diagram Inventory and Migration Manifest

This reference inventories App Service diagram sources for #282 under parent #281. It records source facts and proposed work ownership, not completed migration, reviewed genres, source verification, or rendered visual correctness.

## Purpose and Scope

The [machine-readable manifest](diagram-manifest.json), governed by the [shared inventory schema](diagram-manifest.schema.json), records each Mermaid occurrence with its page-qualified key, source location, heading context, syntax, candidate genre, declared provenance, structural baseline, owner and migration state. The [ADR](adr-diagram-composition.md) explains alternatives and the dependency on #283.

`context.reader_intent` deliberately remains null until reviewed. Target base, extensions and overlays are provisional, not approved composition destinations. `migration.state` remains `not-started`. Evidence-oriented intent is not inferred as a separate syntax type: a lab evidence timeline can be a flowchart or timeline, and must retain its evidence meaning during later review.

## Counting Policy

Every Mermaid fence in tracked Markdown is one occurrence; equal source bodies remain separate occurrences. An asset referenced repeatedly is one asset with multiple usages. The manifest records baseline commit `036376dff4e4c2e919470b51a1cb89ef708d88ea`; counts describe the working tree inventoried for that baseline:

- 399 occurrences appear in 245 diagram-bearing Markdown files. The current tree has 285 Markdown files: 283 tracked files plus the two new inventory and ADR pages (`git ls-files '*.md'` plus `git ls-files -o --exclude-standard '*.md'`).
- 398 are published under `docs/`; one is a repository-only authoring example in `DOCUMENTATION_CONTRACT.md`.
- Four occurrences are excluded: the authoring example and three generated dashboards (content validation, tutorial validation, Golden status).
- 395 Mermaid occurrences require migration; their batch counts sum to 395.
- `visuals[]` separately records two interactive Cytoscape navigation graphs and one learning-path placeholder group, all explicitly excluded pending an owner decision. These are not added to Mermaid batch totals.
- Asset exclusions cover 106 WebPs, six legacy PNGs and two branding SVGs, each in exactly one group. There are no tracked standalone Mermaid, draw.io, PlantUML, or Excalidraw sources.

### Asset Exclusions by Group

Asset groups are path-based claims, not visual verification. Wildcard `paths` entries claim only raster images (`.png`, `.webp`, `.jpg`, `.jpeg`, `.gif`); vector or diagram-source assets require an exact path without wildcard characters, or a matching path rule whose optional `extensions` array explicitly lists dotted suffixes (for example, `[".svg", ".mmd"]`). Asset suffixes and `extensions` entries are case-insensitive (`[".SVG"]` opts into `.svg`); path matching remains case-sensitive. Otherwise they remain in `exceptions.unclassified_assets` for review. App Service claims its branding SVGs by the exact paths `docs/assets/logo.svg` and `docs/assets/favicon.svg`; its other groups use raster-only path patterns, with no `extensions` opt-ins.

## Quality of Classification

### Heuristic Genre Candidates

Syntax decides sequence/state/timeline/chart candidates. For the 355 flowchart/graph blocks, decision nodes or Yes/No labels suggest `decision`, subgraphs without decisions suggest `topology`, mixed signals suggest `unknown`, and other blocks suggest `flow`. All remain `unreviewed`.

A fixed-seed (282), genre-stratified sample of 68 source diagrams was drawn and labeled against `main` at `c169da01b71fc161c1afcf91772edfe4f613a1c3`, after merged PR #291 fixed eight failing blocks. The implementing AI agent read each source diagram and assigned manual labels; this was not an independent human or rendered review. Four sampled bodies had been corrected by that PR before labeling (the Node.js local-run overview and the failed-to-forward-request, SNAT-exhaustion and Windows Java timeout lab timelines). All sampled bodies match that main commit; subsequent Golden-status dashboard regeneration changed the sampled pie's body, so the sample is historical rather than a review of that regenerated body. Syntax candidates agreed on 22/22; heuristic candidates agreed on 39/46 (84.8%). This is advisory sample agreement, not a population accuracy estimate or per-entry approval. Diamonds used only as endpoint/decorative labels, dependency paths without subgraphs, and timeout outcome groups were misleading signals; thresholds were not tuned after labeling.

### Provenance Extraction

The manifest preserves 397 frontmatter diagram entries verbatim: 200 declare `mslearn-adapted`, 197 `self-generated`. Two fences have no matching entry: the repository authoring example and generated content-validation pie. There are no orphan frontmatter entries or unparseable frontmatter records. Extraction completeness does not verify external references, justifications, or Azure behavior.

## Command Reference

Use Python 3.11 with PyYAML; `jsonschema` is optional locally and installed in CI. Commands run from the repository root; the scanner also resolves its root independently of the caller's working directory. It never renders, converts, or verifies source provenance. `--write` writes the manifest and this page's generated blocks; `--check` performs consistency validation, not provenance verification.

Files are decoded as UTF-8 with optional BOM. An undecodable file is skipped and recorded in `frontmatter_unparseable` with its path and decoding error, like unparseable frontmatter; this exception means extraction is incomplete, not that no diagram exists. Duplicate usable frontmatter IDs appear in `frontmatter_duplicate_ids`; only the first entry supplies declared provenance. Missing, null, empty, or non-string frontmatter IDs never attach to a fence.

The scanner is a line-based approximation of how the site renders indentation, not a full Markdown container parser. It errs toward reporting Mermaid-opener-like lines in `unrecognized_mermaid_fences` rather than silently dropping them:

- `html-comment` and `indented-code` are informational: the fence is hidden by a multiline HTML comment or shown as plain indented code. Plain-code state starts at an indented line (at least four columns, with tabs expanded) after a blank line or at the start of the page, while no HTML element is open and no list or container ancestor applies. It continues across blank or indented lines and ends at the first nonblank line with fewer than four columns. A heading or thematic break ends a list, and a line indented four columns or more is code, not a list item. `--check` prints each finding without failing.
- `blockquote`, `list-marker`, and `indented` are blocking findings. The last reason covers container indentation, an indented fence while an HTML element is open, and a lazy continuation directly after prose without a blank line. HTML context is a stack of element names: a tag at the start of a line (up to three spaces of indentation) opens an element unless it is a void element, self-closing or closed on the same line; a closing tag line closes the nearest open element of that name, and a closing tag without an open element is ignored. Intervening paragraphs, headings, lists and code blocks do not close an element. Inline HTML that does not start a line, autolinks such as `<https://example.com>` and comments open nothing. This is a heuristic, not an HTML parser: an element that is never closed (for example an unclosed `<p>`, `<li>` or `<td>`) keeps the context open until a closing tag of an ancestor, and an indented fence inside an open element is reported as blocking even where the site shows plain code. `--write` succeeds and warns once per page, listing only blocking findings; `--check` fails. Move the fence to the top level with at most three spaces of indentation, or show it inside a longer outer fence, then regenerate.
- Fence recognition precedes comment detection. Inline code spans containing comment tokens do not open comments. A multiline comment needs a closing `-->`: an unclosed one is shown as literal text by the site, so it hides nothing, and text inside any fence never closes a comment because the site extracts fences first. Unsupported blocks, including indented generic fences of any language or no language, are consumed through their matching closing fence (even a dedented closer) so later canonical fences remain in sync; shorter fences of the same kind and fences of another kind inside the block are content, and only Mermaid openers produce findings. Another opener of the same kind and at least the same length before a closing fence, or no closing fence, means the block is unclosed and the scan resumes on the next line instead of swallowing the page.
- Recognized outer non-Mermaid fences contain examples, not rendered diagrams, and do not produce unsupported-fence findings. The separate `scripts/validate_mermaid_format.py` policy already rejects indented Mermaid fences, including plain indented code examples; use a longer outer fence for examples.

The shared scanner's classification was checked against Python-Markdown 3.10.2 and pymdownx 10.21.3 on 2026-10-30 in local experiments with synthetic corpora, run for the Container Apps pull request. A 3,300-document grammar corpus had no document where rendered diagrams exceeded recognized non-example occurrences plus blocking findings, and no plain-code document with a blocking finding. A generator of 12,448 balanced documents (HTML wrappers with intervening paragraphs, headings, lists and code, longer generic outer fences with shorter or other-kind inner fences and dedented closers, plain code after neighbouring HTML, and lists ended by headings or thematic breaks) had no such surplus and no blocking finding on plain code; in 4,448 of its HTML-wrapper documents the site shows no diagram although an indented fence inside an open element is reported as blocking, which is the conservative direction. A mutation fuzzer (seeds 11, 12, and 13; 4,000 documents each) found 54, 69, and 60 under-accounted documents respectively (183 of 12,000, about 1.5 %); the remaining minimized cases use corrupted or unbalanced fence syntax. Those harnesses and evidence are not committed here, the experiments were not rerun for App Service, and the scan result of every Markdown file of this repository is identical between the previous and the current scanner version. These measurements come from synthetic corpora, do not estimate how often such patterns occur in real documentation, and are not a rendering guarantee.

Known limitations:

- Info strings with extra words are counted by the first-word `mermaid` rule, but the site shows them as code rather than diagrams.
- A comment that starts after a list marker or blockquote prefix is not tracked.
- Nested list/container structure beyond the less-indented ancestor heuristic may be reported as `indented` when the site shows code. HTML context is a line-start heuristic: a closing tag that does not start a line, or an element that is never closed, keeps or loses context differently from the site, and an indented fence in an open element is blocking even where the site shows plain code. Plain-code continuation is tracked explicitly, but this is not a full container parser.
- Corrupted or unbalanced fence syntax, for example an opener that is never closed, bare marker lines of a different kind, tilde/backtick mixes, or fence markers and comment tokens inside an info string, is parsed differently by CommonMark and by the site's renderer. The scanner uses CommonMark-style boundaries for recognized top-level fences and records their unclosed fences in `unclosed_fences`, but the site can show more diagrams than the scanner accounts for on such a page.

### Validating the Inventory (Blocking CI)

```bash
python scripts/test_diagram_inventory.py
python scripts/diagram_inventory.py --check
```

`--check` validates schema, keys, owning batches, reconciliation, pinned hashes and generated blocks. It does not compare current source to the frozen baseline, render diagrams, or verify provenance. Deterministic fixture reproduction remains blocking; current-tree baseline reproduction is opt-in with `DIAGRAM_INVENTORY_REPRODUCE=1` when the tree is unchanged.

### Regenerating the Manifest

`--write` reads the current working tree and regenerates the whole manifest, recording `baseline.base_commit` as metadata (pass `--base-commit` to pin it); it does not read the tree at that commit or retain separate baseline records and current-tree observations. Run `--verify-tree` before rewriting to see removed and changed records. Reviewed planning fields are preserved by key, while a reviewed classification is preserved only when the diagram body's `baseline.source_sha256` is unchanged; a changed body receives a fresh, unreviewed heuristic classification and must be reviewed again.

```bash
python scripts/diagram_inventory.py --write --base-commit "$(git rev-parse HEAD)"
```

Use an explicitly reviewed baseline commit when rebasing the inventory. Without an override, subsequent writes preserve the existing base commit. Do not edit the manifest or generated blocks by hand.

### Migration Progress States

Batch owners edit `target`, `context.reader_intent`, and `migration` by key; these planning fields survive body changes and regeneration.

| Migration state | Meaning | `exception` |
|---|---|---|
| `not-started` | Migration has not begun. | `null` |
| `in-progress` | The owning batch is migrating the diagram. | `null` |
| `completed` | The owning batch records migration as complete. | `null` |
| `exception` | Migration has an explicitly recorded exception. | Nonblank explanation string |

These are owner-maintained progress states, not proof of rendering, source verification, or review approval.

### Checking Tree Drift (Advisory)

```bash
python scripts/diagram_inventory.py --verify-tree
```

This compares extracted diagram records with the baseline; it does not report extraction completeness. Consult `unrecognized_mermaid_fences` through `--check` for blocking extraction findings. A drift-free result alone does not establish a complete inventory.

The JSON categories are `added` and `removed` keys; `moved` key changes with identical bodies; `changed` body hashes; `reclassified` genre, syntax type, or assignment changes; `provenance` changes to the complete provenance record; and `relocated` changes to the same key's line, end line, or heading path. `assets` lists changed exclusion-group path sets as `{group, added, removed}` records, with `group: null` for the unclassified-asset set; `visuals` lists keys added, removed, or changed in non-Mermaid visual records. Paths are compared as sets, not list order. Drift remains advisory (exit zero); adding `--strict` makes any non-empty category fail. This does not refresh Azure capture or validation dates.
